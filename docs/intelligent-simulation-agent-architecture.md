## 1. 理念

### 1.1 什么是"智能仿真应用系统"

**传统仿真软件的使用链条**：
```
用户 → GUI 点菜单 → 设置参数 → 跑算例 → 人工后处理 → 读图读数 → 写报告
```
每一步都依赖 *人的经验* 与 *人的时间*。专家 70% 时间消耗在**流程操作**而非**物理判断**上。

**智能仿真应用系统把链条改造为**：
```
用户 → 自然语言表达意图
        ↓
       Agent（理解 / 规划 / 调用 / 验证 / 交付）
        ↓
       仿真内核 + 已有物理模型 + 知识库
        ↓
      可视化 / 结论 / 报告
```

关键转变：**仿真内核不变，外层交互方式从"GUI 驱动"变成"意图驱动"**。Agent 是把"领域专家的经验流程"与"确定性计算内核"连起来的那层。

### 1.2 ChatCFD / SimGraph 在框架中的位置

| 应用 | 问题域 | 主要输入 | 主要输出 | 对 Agent 的核心要求 |
|------|--------|----------|----------|---------------------|
| **ChatCFD** | CFD 仿真结果分析 | CGNS / VTK / OpenFOAM 结果文件 | 数值、图像、对比、报告 | 工具调用、物理量推断、后处理编排 |
| **SimGraph** | 几何 / 网格 / 前处理场景 | CAD、网格、样例库 | 场景图、前处理流程、自动化脚本 | 图结构理解、流程复用、模板推理 |

两者共享同一套底层：**Agent 服务层 / 知识库 / 约束体系 / 记忆系统**。差异只在 *MCP 工具集* 与 *算法注册表*。这正是"框架"的意义 — **换问题域只换工具集，不重写 Agent**。

### 1.3 最终目标：一体化智能仿真软件生态

一体化意味着：

- **能力统一发现**：新加一个求解器 / 一个算法 / 一个物理模型 → 通过标准接口注册 → Agent 自动可用。
- **知识统一沉淀**：跨项目、跨软件、跨版本的工程经验可被检索、可被验证。
- **交互统一范式**：不管底层是 OpenFOAM、Fluent、自研求解器，用户面对的都是"自然语言 + 可视化"。
- **生态统一进化**：所有使用产生的数据（成功的分析、失败的尝试、用户偏好）都能反哺系统本身。

图注（对应 PRD §2.1 "要点"的同级说明）：

- **六层而非五层**：在 L1–L5 之外单列 L0 知识库层，横贯所有上层。这一层的定位不是"存储"，而是"AI 的词典 + 仲裁者" — 决定 LLM 怎么理解输入，也决定计算结果能不能被接受。
- **L5 应用层共享下层**：ChatCFD 与 SimGraph 共享同一套 L4/L3/L0，差异只在 L2 工具集。**换应用不重写 Agent**，这是"框架"二字的技术实质。
- **L4 的主/子 Agent 结构**：主 Agent 是用户的唯一对话入口；子 Agent 在重任务时被派出去，失败不影响主对话。诊断子 Agent 是 Phase 2 的主动感知起点 — 不等提问、主动扫异常。
- **L3 三层约束 × MCPClientPool**：约束三层（Harness/Skill/Prompt）越关键的越往下沉；MCPClientPool 同时接后处理 / 记忆 / 前处理 / 求解器四条线，Agent 端感觉不到区别。
- **L2 是服务层, 不只是引擎**：post_service（后处理主力）· Mempalace（记忆服务）· simgraph_service / openfoam_adapter（规划）四个独立进程并列。MCP（summary 给 LLM）与 HTTP（大数据给前端）是 post_service 同引擎的两个出口，不重复加载 VTK；SessionState 按 session_id 严格隔离，多用户并发不串扰。
- **记忆是一等公民, 三类分工清晰**：
    - **Insight Log** (L4 内)：对话轨迹, 每轮 JSONL — 用于离线分析、Skill 迭代
    - **Analysis Archive** (L2 post_service 内)：按文件 md5 绑定的**精确数值结果** — "某个文件上算过什么"
    - **Mempalace** (L2 独立进程)：跨会话、跨项目的**模糊语义记忆** — "某人/项目的偏好和经验"
   三者不互相替代。Mempalace 通过 `AgentSession.memory_wing` 与 L4 配对，loadFile 时按 wing 自动检索注入 Prompt。
- **L1 三类内核并列**：自研 C++（已有高精度能力）+ 开源 VTK（兜底）+ 外部求解器 Adapter（生态入口）。三者都通过算法注册表进入 L2，**对 Agent 无差别暴露**。
- **L0 三类知识互不替代**：语义（帮 AI 理解）+ 验证（防 AI 犯错）+ 经验（让 AI 越用越懂）。三者分别对应"AI 开口前、计算返回后、下次对话前"三个时间点。

各层承诺不变：
- **L1 只管正确计算**，不关心谁在调用。
- **L2 把 L1 的能力声明成可注册的算法**，统一返回 `{type, summary, data, output_files}`。
- **L3 用 MCP 把 L2 暴露给 LLM**；Harness 在此层拦截风险调用。
- **L4 只调 L3 暴露的工具**，不碰 VTK、不写文件路径。
- **L0 横贯所有层**，既给 L4 提供语义（什么叫"压力"），也给 L2 提供校核（结果合不合理）。

### 2.2 数据流（三通道模型）

核心洞察：**LLM 的上下文很贵，网格数据很大，经验的价值跨越会话**。三种数据的生命周期、大小、用途完全不同，必须走三条独立通道。

```
╔═════════════════════════════════  运行时三条数据通道  ════════════════════════════════════╗

三通道对照：

| 通道 | 谁读谁写 | 数据量 | 是否过 LLM | 核心目的 |
|------|----------|--------|:----------:|----------|
| ① 对话 | L4 ↔ L2 (MCP SSE) | KB | ✅ 过 | 让 LLM 做**决策** |
| ② 渲染 | 前端 ↔ L2 (HTTP) | 几十 MB – 几百 MB | ❌ 不过 | 让前端做**可视化** |
| ③ 反哺 | L4/L2 → L0 | KB (累积) | ❌ 不过 | 让系统做**自进化** |

这三通道的分工是整个系统最重要的工程决定：**让 LLM 做决策（窄带高智能），让 HTTP 做搬运（宽带纯流量），让知识库做记忆（慢变高价值）**。三者任何一条混到另一条的通道都会出事 — 大数据过 LLM 爆 token，决策跳过 LLM 丢智能，经验不沉淀系统不进化。

#### 单次计算的完整链路（以"算 wall 的升力系数"为例）

```
  User   "算 wall 的升力系数"
   │
   │ ① 对话通道 (WS)
   ▼
  L4 主 Agent
   │  Harness 预检 (OK) → Skill 命中 force_moment → 发现缺 ref_area
   │
   │  LLM 回: "请提供参考面积"                         ─────▶  User
   │                                                           │
   │                    User: "0.12"                   ◀──────┘
   │
   │  LLM 生成 calculate(method="force_moment", zone="wall", ref_area=0.12)
   │
   │ MCP(SSE)
   ▼
  L3 MCPClientPool → 路由到 post_service (SSE)
   │
   ▼
  L2 PostEngine.calculate(...)
   │  SessionState[session_id].post_data → get_vtk_data()
   │  algorithms/force_moment.execute(post_data, {ref_area:0.12})
   │    └─▶ L1 RomtekAnalysis::ForceMomentIntegtal (C++)
   │          └─▶ 返回 {force, moment, coefficients}
   │
   │  L0 value_ranges 校核:  CL=0.35 ∈ [-2, 2]  ✅
   │  L0 archive 查历史:     同 md5 上次 CL=0.36, 差 3%  ✅
   │
   │  返回 { type:"numerical",
   │         summary:"wall CL=0.35, CD=0.012, 与 2026-04-18 结果差 3%",

   │         output_files:[] }
   │
   ▲ summary 摘给 LLM                        data 原样给前端 Artifact (② 渲染通道)
   │
  L4 主 Agent
   │  LLM 说: "wall 区域升力系数 CL=0.35, 阻力系数 CD=0.012"
   │
   │  ③ 反哺通道:
   │    · Insight Log 追加 {intent:"force_moment", resolution:"tool_resolved", ...}
   │    · Archive 写入 .chatcfd/analyses/{md5}/force_moment_*.json

这条链路上的每一步都对应架构图里具体的层和组件。**这就是"一次对话"在六层架构里实际走过的路径**。

### 2.3 技术架构

| 层次 | 选型 | 为什么 |
|------|------|--------|
| LLM | Qwen / Claude / GPT（LiteLLM 统一） | 避免锁定；不同任务用不同模型 |
| Agent 框架 | 自研 Python + FastAPI + WebSocket | 框架黑盒会让 Harness 难做；仿真场景需要可控 |
| Tool 协议 | MCP（Model Context Protocol） | 工具标准化，跨 LLM 兼容，生态起势 |
| 计算服务 | FastAPI + FastMCP 同进程 | MCP SSE + HTTP API 共享 PostEngine，不重复加载 VTK |
| 数据层 | PostData 薄封装 + `vtk_to_numpy` 零拷贝 | 仿真数据 GB 级，禁复制 |
| 几何/物理 | VTK 9.4.1 + 自研 C++（RomtekIODriver / RomtekVtkAlgorithm） | 标准 VTK 兜底，C++ 模块承接自研高精度算法 |
| 前端 | Vue.js + VTK.js | 客户端 WebGL 渲染，服务端零渲染负担 |
| 记忆 | Analysis Archive（结构化） + Mempalace（语义） | 精确结果与模糊经验分离 |

### 2.4 能力层次架构（L0 – L4）

| 能力层 | 内容 | 示例 |
|--------|------|------|
| **L0 感知** | 理解文件里有什么、用户说的是什么 | 加载 CGNS → 识别 zone/标量名；"压力" → `Static_Pressure` |
| **L1 计算** | 对已知对象做确定性计算 | 积分、切片、流线、统计 |
| **L2 组合** | 多步骤协同 | "沿 X 切 10 个片 + 按涡量着色 + 合成 GIF" |
| **L3 对比与归因** | 在多份数据之间找差异、给原因 | 实验 vs 仿真、两个 case 的差异分析 |
| **L4 判断与建议** | 超出数值，给出物理判断 | "这个 CL 偏低可能是因为网格在前缘不够细" |

ChatCFD 当前稳定在 **L0 – L2**，**L3** 通过子 Agent 打通，**L4** 依赖知识库与人的经验沉淀 — 这也是我们为什么要做知识库。

### 2.5 数据架构

仿真数据和 AI 系统数据在本质上是两个生命周期，必须分开管理：

```
 ┌─────────────────────── 仿真数据（只读） ───────────────────────┐
 │  CGNS / VTM / OpenFOAM case   ← 用户工程数据，系统不改           │
 │  PostData 零拷贝访问，写保护 writeable=False                     │
 └────────────────────────────────────────────────────────────────┘

 ┌─────────────────────── 运行时数据（会话生命周期） ─────────────┐
 │  SessionState { PostData 引用、output_dir、加载历史 }            │
 │  session 关闭 → 释放                                             │
 └────────────────────────────────────────────────────────────────┘

 ┌─────────────────────── 沉淀数据（跨会话） ────────────────────┐
 │  Analysis Archive   .chatcfd/analyses/{md5}/  （结构化、可验证）  │
 │  Mempalace          ~/.mempalace/             （语义、跨项目）   │
 │  Insight Log        agent/insight.jsonl        （需求分布统计）  │
 └────────────────────────────────────────────────────────────────┘

 ┌─────────────────────── 知识数据（静态资产） ──────────────────┐
 │  physical_mapping.json    （求解器 → 标准物理量）                 │
 │  algorithms/*.py          （方法注册表）                          │
 │  skills/*                 （工作流模板）                          │
 │  value_ranges / ambiguity （物理合理范围、歧义表）                │
 └────────────────────────────────────────────────────────────────┘
```

**写保护纪律**：所有从 VTK 拿到的 numpy 数组 `writeable=False`。任何算法要改 → 显式 `.copy()`。这样避免"某个算法无意改了原始数据，后续所有分析都错"。

**主 Agent 自己做 vs 派子 Agent 的决策表**：

| 用户请求特征 | 主 Agent 处理 | 派哪个子 Agent | 原因 |
|--------------|:-------------:|----------------|------|
| 单次 load / calc / compare / export | ✅ 直调 MCP | — | 一次 tool_call 就完了, 不值得 spawn |
| 多文件对比（>=3 份数据） | ❌ | 对比子 Agent | 遍历 + 归因需要独立上下文, 避免污染主对话 |
| 需要运行 Python / Bash 脚本 | ❌ | Coding 子 Agent | 必须走 Harness 的 explicit confirm 通道 |
| "帮我把今天的分析整理成报告" | ❌ | 报告子 Agent | 聚合多个 archive 条目, 独立长上下文 |
| "这个 case 有什么异常" （Phase 2） | ❌ | 诊断子 Agent | 主动扫描型, 与主对话异步 |
| 单个 zone 的 min/max | ✅ 直调 MCP | — | 原子任务 |
| 模糊的 "看看结果" | ✅ 反问澄清 | — | 反问也是主 Agent 的能力, 不派子 |

**核心边界**（重复强调, 因为最容易被违反）：

- 主 Agent **只**做对话编排, 不碰业务执行。任何"写文件 / 跑进程 / 调 VTK"的冲动, 都是派子 Agent 的信号。
- 子 Agent **只**有一次机会 — 完成任务, 返回结果, 销毁。没有"继续上次的子 Agent"。
- 子 Agent 之间**不通信** — 需要协同的任务由主 Agent 串行编排, 不让子 Agent 互相调。
- 任何一个子 Agent 的失败都**不能**影响主对话 — 主 Agent 捕获异常, 给用户一句人话解释, 会话继续。

### 3.2 约束三层（Harness / Skill / Prompt）

| 层 | 属性 | 实现 | 典型约束 |
|----|------|------|----------|
| **Harness** | 硬约束，代码强制 | Python 装饰器、调用前拦截 | 路径必须在白名单；超过 N MB 文件拒绝；AI Coding 必须用户确认 |
| **Skill** | 中约束，流程引导 | MCP Prompt 模板 + System Prompt 注入 | 分析前先 listFiles；力系数计算前必须确认参考面积 |
| **Prompt** | 软约束，行为规范 | System Prompt 文本 | 别编物理量名；不会就反问；summary 要简洁 |

**为什么分三层**：LLM 的"记得做"与"真的做了"是两回事。越关键的约束越往下沉 — 能写在代码里就不留给 Prompt。

### 3.3 和 ChatBot 的差别

一个好的 CFD Agent 不是"能聊 CFD 的 ChatBot"，而是：

1. 它**有工具**：调用 `calculate(method="force_moment")` 得到真值，不是生成貌似专业的文字。
2. 它**有记忆**：上一次分析的 md5、上一次你说"参考面积用 0.12"都能在后续命中。
3. 它**有边界**：文件超了就拒绝，路径野了就拦截，代码改执行前必须你点头。
4. 它**有验证回路**：计算结果进 value_range 校核；对结果不合常理的主动提示。

## 4. 知识库体系

> 知识库在我们的系统里有两个并列使命：
> - **为 AI 提供知识支撑** — 让 LLM 做决策时有依据，而不是编造。
> - **为执行结果提供确定性验证的来源** — 让"AI 给的答案"可以被独立校验。

### 4.1 两类知识

```
                          知识库
                          │
           ┌──────────────┴──────────────┐
           │                             │
     AI 语义知识                   确定性验证知识
   （用于推理 / 补全 / 消歧）     （用于校核 / 拒绝 / 标注）
           │                             │
 ┌─────────┼─────────┐         ┌─────────┼──────────┐
 │         │         │         │         │          │
物理量   算法       工作流    取值范围  关系约束   标杆数据
映射表   文档       模板      (ranges)  (守恒/     (基准算
         (docs)     (skills)            无量纲)    例/实验)
```

**两类知识的使用方式是不对称的**：
- AI 语义知识 → 注入 Prompt / Tool description，LLM 读。
- 确定性验证知识 → 代码层在结果返回前执行，LLM 不能绕过。

### 4.2 当前已落地

| 知识资产 | 位置 | 类型 | 状态 |
|----------|------|------|------|
| 物理量映射表 | [post_service/config/physical_mapping.json](post_service/config/physical_mapping.json) | 语义 + 验证（含 value_ranges / ambiguity） | ✅ 已用 |
| 算法注册表 | [post_service/algorithms/](post_service/algorithms/) | 语义（NAME/DESCRIPTION/DEFAULTS） | ✅ 已用 |
| Skill 工作流模板 | [agent/skills.py](agent/skills.py) | 语义 | ✅ 已用 |
| 分析存档 | `.chatcfd/analyses/{md5}/` | 验证（历史结果按文件绑定） | ✅ 已用 |
| Mempalace 语义记忆 | `~/.mempalace/` | 语义（跨项目偏好 / 经验） | 🚧 集成中 |
| 基准算例库 | 待建 | 验证（标杆 case + 参考解） | 📋 规划 |
| 物理守恒校核 | 待建 | 验证（质量 / 动量 / 能量） | 📋 规划 |

### 4.3 知识如何被 Agent 消费

**读路径 1 — 语义**：
```
用户问 "看压力" 
  → Agent 接到消息
  → Skill 层在 System Prompt 里注入映射表
  → LLM 生成 calculate(scalar="pressure")
  → PostData 层内部把 "pressure" 解析为 "Static_Pressure"
  → 取 numpy 返回
```

**读路径 2 — 验证**：
```
算法执行 → 得到 CL=0.35
  → value_ranges 校核：CL 合理区间 [-2, 2]？是
  → 物理守恒校核：表面积分 - 体积分残差？< 阈值
  → 历史对比：同 md5 上次算的 CL = 0.36，差 3%，正常
  → 返回 summary
```

**这两条路径合在一起**，才让 Agent 从"能说话"变成"说得出、算得准、扛得住追问"。

## 5. 已有能力如何接入，准确性如何验证

> 本节是我们从项目 Claude Code 对话与 PR 历史中总结出的实际工程方法。不谈"应该怎样"，只谈"我们是怎么做的"。

### 5.1 能力接入的四条标准路径

```
① 原子算法层         → 落到 post_service/algorithms/xxx.py 插件
② 复合工具层         → 落到 post_service/mcp_tools/（极少数情况）
③ 子 Agent 能力      → 落到 agent/sub_agent/（需要多步编排时）
④ 外部仿真软件接入   → 走 MCP Server 或 adapter（见 §7）
```

**每条路径都是单向的**：下一条只在前一条不够用时启用。绝大多数新能力最终都落在 ① — 也就是"加一个 `.py` 文件"。

#### 算法接入最小闭环

每个 `algorithms/*.py` 只需要四个约定：

```python
NAME = "force_moment"
DESCRIPTION = "对 zone 做力/力矩积分，返回升力/阻力系数"
DEFAULTS = {"ref_area": 1.0, "ref_velocity": 1.0, ...}

def execute(post_data, params) -> dict:
    ...
    return {
        "type": "numerical",
        "summary": "wall CL=0.35, CD=0.012",     # LLM 只看这行
        "data": {...},                            # 前端 artifact
        "output_files": []                        # 下载/可视化
    }
```

注册是自动的 — `algorithm_registry.py` 启动时扫目录。LLM 看到的"工具菜单"是*从算法自己的 DESCRIPTION 聚合出来的*，**算法作者一次写，整条链路自动对齐**。

### 5.2 准确性三层验证

| 层 | 在哪一步 | 检查什么 | 失败如何 |
|----|----------|----------|----------|
| **T1 类型与契约** | 算法返回时 | 返回 `{type, summary, data}` 齐全？`summary` 是字符串？ | 框架直接抛错，LLM 收不到空响应 |
| **T2 物理合理性** | Engine 返回前 | 值在 `value_ranges` 内？守恒残差 < 阈值？量纲匹配？ | 在 summary 里标注 "⚠️ 超出常规范围"，让 LLM 必须向用户提示 |
| **T3 基准回归** | CI / 定期 | 基准算例的已知解 vs 当前版本输出 | 差异 > 容忍度 → CI 红 |

T1 保证**接口能用**，T2 保证**数值可信**，T3 保证**回归不破**。三层之间严格互不替代。

### 5.3 从 Claude Code 对话里学到的实操经验

我们通过 Claude Code 协作开发 ChatCFD 的过程本身，就是"Agent 如何使用 Agent 能力"的一次真实样本。关键沉淀：

1. **工具数量要少而精**。Claude 一开始给 LLM 暴露了 12 个工具，LLM 频繁误选。砍到 **6 个互斥工具**后错误率骤降 — 对应到 PRD §3.1 的"最少工具数"原则。
2. **summary 必须算法自己写**。靠 LLM 解析 `data` 总结 → token 成本高、出错率高。让算法作者（最懂结果的人）写 summary → 稳定。
3. **不猜是比猜得准更重要的能力**。力系数需要参考面积 — LLM 的天然倾向是填 `1.0` 蒙过去。Skill + Prompt + Harness 三层联动，才让它学会"先反问"。
4. **会话状态要显式**。早期每个 calculate 都要求 LLM 重新填 file_path，LLM 经常填错。改为 SessionState 缓存后，LLM 只需给 zone/method 即可。
5. **GIF / 多步任务要原子化**。早期 "切 10 片 + 合成 GIF" 被 LLM 拆成 10 次 render + 1 次 run_python，慢且出错。现在一次 `calculate(method="slice", output_images=true)` 完成 — 复杂度留在算法里，不留给 LLM。

这 5 条写在 [docs/test-conversations.md](docs/test-conversations.md) 与多个 PR 的回归测试里。它们是"智能体工程纪律"的本地化版本。

## 6. 难点分析

### 6.1 为什么开源世界"Agent × 仿真"的组合几乎空白

工业仿真与主流 AI Agent 社区的重合度极低，根因至少六条：

1. **数据闭源**。仿真结果往往涉及型号、合规、密级，做不了公开 benchmark → 社区缺训练集 / 评测集。
2. **计算重**。一次 CFD 算例动辄几小时到几天，Agent 的"试错式探索"成本无法承受。
3. **工具异构**。Fluent、CFX、STAR-CCM+、OpenFOAM、自研求解器的 API / 文件格式 / 概念词典完全不同，缺标准接口层。
4. **知识非编码化**。"这个 case 为什么算不收敛" 是老工程师脑子里的，论文里没有，代码里更没有。
5. **后处理非文本**。图像 / 几何 / 标量场不像代码那样可以被 diff，LLM 不擅长直接"看"。
6. **对错误零容忍**。一篇错代码可以回滚，一个错仿真结论可能让型号返工 — 信任门槛天然高。

### 6.2 把智能体装进仿真平台的六大核心难点

| 难点 | 具体表现 | ChatCFD 的应对 |
|------|----------|---------------|
| **①意图到工具的映射** | 用户说"看下这块不对劲"— 工具层没有"诊断"方法 | Skill 层把模糊意图降阶到"查看 + 统计 + 切片"组合 |
| **②大数据通道** | 几十 MB 网格数据塞给 LLM → 爆 token | 双通道：summary 给 LLM，数据直连前端 |
| **③术语多源异名** | 同一个"压力"在 10 个求解器有 10 个名字 | 物理量映射表 + PostData 层透明解析 |
| **④幻觉的危险** | LLM 编一个不存在的标量名，算法直接炸 | Tool description 列候选；算法返回 "not found" 不是 silent zero |
| **⑤会话记忆耦合** | 多用户并发共享一个 VTK 对象 → 相互污染 | SessionState 严格按 session_id 隔离 |
| **⑥可验证性** | AI 说 CL=0.35，怎么证明是对的 | value_ranges + archive 历史 + 基准回归三叉验证 |

这六点里的任意一条做不到，Agent 就会"看起来聪明、用起来危险"。

## 7. 已有物理模型如何融入

### 7.1 物理模型接入的四个层次

不同层次的接入，改造成本和回报完全不同：

```
                 改造成本        Agent 能做的事
  L₀  裸调用     最低            执行、读日志（黑盒）
  L₁  包一层     低              参数选择、结果取值
  L₂  语义化     中              理解边界条件、修改物理设置
  L₃  可组合     高              多模型协同、自动切换求解器
```

目标永远是 L₂ 及以上。**L₀ 是起点，不是终点**。

### 7.2 以 OpenFOAM 为例的全流程接入

OpenFOAM 是最典型的开源 CFD — 文件系统即项目结构（`0/ constant/ system/`），命令行驱动，支持丰富的物理模型（k-ε, k-ω SST, LES, 多相流 …）。接入分四步：

#### 步骤 1 — 文件结构感知（L₀ → L₁）
为 OpenFOAM case 写一个 reader adapter：

```python
# post_service/adapters/openfoam_case.py
class OpenFOAMCase:
    def __init__(self, case_dir):
        self.controlDict = parse_dict(case_dir + "/system/controlDict")
        self.turbulenceProperties = parse_dict(...)
        self.boundary = parse_dict(case_dir + "/constant/polyMesh/boundary")
        self.time_dirs = sorted_time_dirs(case_dir)
    def list_fields(self, time="latestTime"):  ...
    def load_field(self, name, time):          ...   # 走 VTK OpenFOAM Reader
```

这让 PostEngine 能把一个 *case 目录* 当成一个"文件"处理。用户只需 `加载 D:/case/pitzDaily`。

#### 步骤 2 — 物理量映射注册（L₁）
扩展 `physical_mapping.json`：

```json
"solver_profiles": {
  "openfoam": {
    "mappings": [
      {"raw_name": "p",     "physical_name": "pressure",    "unit": "Pa", "conversion": 1.0},
      {"raw_name": "U",     "physical_name": "velocity",    "type": "vector"},
      {"raw_name": "k",     "physical_name": "tke"},
      {"raw_name": "omega", "physical_name": "omega_sdr"},
      {"raw_name": "nut",   "physical_name": "turbulent_viscosity"},
      ...
    ]
  }
}
```

只要这一步做了，**所有已有算法不用改** — Agent 让"看 k-ω SST 的湍流粘性"时，PostData 自动找到 `nut`。这是"映射表放在数据层而非算法层"的红利。

#### 步骤 3 — 物理模型语义化（L₂）
把"湍流模型选择"这样的**业务动作**暴露成工具：

```python
# post_service/algorithms/openfoam_turbulence.py
NAME = "switch_turbulence_model"
DESCRIPTION = "切换 OpenFOAM 湍流模型，并更新 turbulenceProperties"
DEFAULTS = {"model": "kOmegaSST"}
CANDIDATES = ["kEpsilon", "kOmegaSST", "Spalart-Allmaras", "LES-Smagorinsky"]
def execute(post_data, params):
    case = post_data.case  # OpenFOAMCase
    case.write_turbulence_properties(params["model"])
    return {"type":"file", "summary": f"已切换为 {params['model']}", ...}
```

重点是：**把 OpenFOAM 的 `.foam` dict 语义抬升为"业务概念"**。Agent 不用理解 `turbulenceProperties` 的语法，只要知道"湍流模型"。

#### 步骤 4 — 可组合（L₃）
把"跑仿真 + 取结果 + 比对实验"变成一条工作流：

```python
# agent/skills/openfoam_validation.py
@skill("validate_openfoam_case")
def workflow():
    """
    1. 让用户指定 case 目录和实验数据 CSV
    2. 调 runCase 跑到收敛
    3. 调 loadFile 加载最新时间步
    4. 调 compare 对比实验 CSV
    5. 如果误差 > 阈值，提示换湍流模型并询问是否重算
    """
```

到这一步，Agent 已经不只是"代操作"，而是在**代替一个初级工程师完成一个闭环的验证流程**。

### 7.3 接入的三个通用原则

1. **Adapter 层永远薄**。不要在 adapter 里塞业务逻辑 — 所有业务逻辑都应该落到算法 / Skill 层。
2. **原生模型不碰**。不修改 OpenFOAM 源码、不魔改 Fluent journal 语义；所有改造发生在*外面*。
3. **旧 case 要能跑**。新接入不应要求用户把历史 case 全部重跑 — 通过 adapter 直接读旧产物。

这三条保证生态是"叠加"而非"替换"。

## 8. 演进路线

### 8.1 四个方向的当前位置

| 目标 | 含义 | 当前位置（ChatCFD） |
|------|------|--------------------|
| **自主感知** | 不等指令，主动发现数据里的异常 | 🟡 Insight Log 捕捉需求分布；value_ranges 会警告，但尚未"主动扫描" |
| **多智能体** | 多个专职 Agent 协作完成任务 | 🟢 主/子 Agent 分工已就位；跨应用（ChatCFD × SimGraph）协作是下一步 |
| **自主执行** | 从"AI 建议"到"AI 直接动手" | 🟡 只读路径（后处理）已放开；写路径（跑仿真）仍要用户确认 |
| **自进化** | 用户越用，系统越懂 | 🟡 Mempalace 收集偏好；但"自动调整 Skill/Prompt"尚未闭环 |

### 8.2 分阶段演进

```
今天：意图驱动的后处理助手
 │
 ▼
 Phase 2：主动感知
 · loadFile 后自动扫描 → "你的 CL 比历史低 15%，要看差异吗"
 · 网格质量预检、边界收敛提示
 │
 ▼
 Phase 3：仿真内的多智能体
 · 前处理 Agent（SimGraph）← 协作 → 后处理 Agent（ChatCFD）
 · 诊断 Agent 独立于主对话，在后台扫异常
 │
 ▼
 Phase 4：受控的自主执行
 · 写路径放开：AI 调 runCase / 改 controlDict，但每个修改保留 diff、可回滚
 · "Dry run" 模式：先给 plan，再执行
 │
 ▼
 Phase 5：自进化生态
 · 用户操作 → Insight Log → Skill 自动更新
 · 新算例产生的经验 → Mempalace → 下次同类问题被主动召回
 · 跨组织的经验可选择性共享
```

### 8.3 自进化的闭环长什么样

```
  用户操作
     │
     ▼
  Insight Log (结构化记录 who/when/what/resolution)
     │
     ├── tool_resolved           → 加入基准回归库
     ├── ai_coding_resolved      → 看是否值得沉淀为算法
     ├── workflow_bounced        → 触发 Skill 模板迭代
     └── unresolved              → 进入人工 review 队列
            │
            ▼
       Skill / 知识库 / 算法注册表 更新
            │
            ▼
       下一位用户受益
```

这里的关键不是"让 AI 自己训练自己"，而是**让系统从真实使用数据里稳定地、可审计地提取改进信号**。我们不追求黑箱自进化 — 我们追求**可解释的自进化**。

## 9. 愿景

一体化智能仿真软件生态，在我们的定义里，不是"一套大一统软件"，而是：

1. **一个统一的接入规范** — 新求解器、新后处理、新前处理走同一套 MCP + 物理量映射 + Skill 协议。
2. **一个共享的知识库** — 物理量字典、value_ranges、基准算例、工程经验跨应用复用。
3. **一个可插拔的 Agent 层** — ChatCFD 是它的一个应用，SimGraph 是另一个；明天可以加 ChatStructural、ChatElectromag。
4. **一个贯通的记忆系统** — 工程师在 ChatCFD 里做的判断，到了 SimGraph 里不需要再说一遍。
5. **一个可被审计的决策链** — 每一个 AI 的动作都有证据链：哪条知识支撑、哪个算法执行、哪条校核验证。

我们相信仿真行业的下一步不在于更快的求解器，而在于**把专家的经验沉淀为系统的能力**。这个沉淀的载体，就是智能体。

## 附：与客户对话的五句话版本

1. **Agent 不是 ChatBot**。它有工具、有记忆、有边界、有验证 — 四样少一样都不是 Agent。
2. **最大的工程约束不是模型能力，是数据流与信任**。双通道架构和知识验证是我们的核心设计。
3. **知识库既是 AI 的养料，也是 AI 的裁判**。没有确定性验证，Agent 在仿真里寸步难行。
4. **接入已有软件的路径是"叠加"而非"替换"**。OpenFOAM 一类软件通过 adapter + 物理量注册 + Skill 封装，四步进入平台，原生不动。
5. **一体化智能仿真生态的载体是 Agent**。它把已有求解器、已有经验、已有数据，组织成一个"越用越聪明"的系统。
